// Keeping Static Deployments Boring

Why simple deployment workflows remain resilient, and why this new version of JRodrigo.com is being built for an AI-assisted editing workflow instead of the old WordPress stack.

  • NOTE-001
  • Published Feb 15, 2026
  • published
  • ~4 min read
  • deployment
  • reliability

When a project does not need runtime state, static deployment is often the most durable option.

The fewer moving parts in production, the easier it is to recover from mistakes. That principle is also shaping this new version of JRodrigo.com: a website that should be easy to inspect, easy to regenerate, and easy to change with the tools we actually use now.

why rebuild the site now

The old website workflow was too dependent on WordPress conventions. WordPress is useful for many sites, but for this project it made small edits feel heavier than they needed to be. Content lived behind an admin interface, design changes were coupled to theme behavior, and AI-assisted edits were harder to review because the final result was not just a readable file in a repository.

The new direction is intentionally simpler: static HTML generated from clear source content, shared styles, and a structured knowledge base. Instead of treating the site as a black box managed through a dashboard, the site becomes a set of files that can be read, reviewed, diffed, edited, and deployed.

// observation

The goal is not to make the website more complex because AI is involved. The goal is the opposite: make the website plain enough that AI tools can help without hiding what changed.

AGENTIX as context

The AGENTIX knowledge base gives the site a structured memory of J.Rodrigo's projects, professional profile, technologies, platforms, websites, experience, sources, and reusable messages. Each Markdown file is designed to be self-contained, machine-readable, and still understandable by a human reviewer.

That matters because AI is only useful here if it can work from grounded context. A project description, a service page, a note, or a wiki entry should not be invented from scratch every time. It should be assembled from traceable facts, then edited into a page that matches the tone and visual language of the website.

AI-assisted does not mean unreviewed

This workflow is closer to engineering than publishing through a CMS. AI can propose structure, rewrite copy, adapt templates, or generate a page variant, but the result still lands as normal HTML, CSS, and JavaScript that can be inspected line by line.

  • The source should stay readable in a repository.
  • The generated page should preserve the global layout, navigation, footer, background, and visual variables.
  • Metadata such as dates, tags, status, and routes should remain explicit.
  • Interactive behavior should be small, local, and understandable without packed or hidden loaders.

This is why a static deployment is attractive for the new site. It makes the AI part safer because the final artifact is concrete. There is no hidden database state, no plugin stack, no theme override that only appears after clicking through an admin panel.

leaving WordPress behind

WordPress made sense in the previous era of website editing: log in, open a page, modify content, publish. The new era is different. The editing environment is now closer to a collaborative technical workspace where AI can read project context, compare files, generate alternatives, and produce a reviewed patch.

For JRodrigo.com, that means the website should behave like a technical project, not like a fragile admin surface. The same repository-oriented workflow used for software can also support notes, project pages, wiki pages, and future experiments.

what boring actually means

Boring deployment is not lazy deployment. It means the surface area is small enough that you can hold the entire thing in your head at 11 PM without coffee. It means a full deploy takes less than two minutes. It means the rollback strategy is upload the previous folder.

For this site, boring is also what makes iteration possible. A page can be regenerated, reviewed, previewed, and replaced without fighting a CMS. If something breaks, the recovery path is visible: open the file, inspect the change, revert or edit, and deploy again.

the failure surface rule

A useful mental model: imagine everything in your deploy chain going offline simultaneously. Now ask — how long does it take to restore the site from scratch, starting from the repo?

  • If the answer is under five minutes, your deploy is resilient.
  • If the answer involves reading plugin documentation first, it is fragile.
  • If the answer depends on a visual editor behaving correctly, it is harder to automate.
  • If the answer is "I'm not sure", fix that before you ship anything else.

Static files stored in a repo and served from a plain host pass this test almost by definition. The deployment is deterministic: same input, same output, every single time.

practical notes

A few things I want to keep consistent across this rebuild: one shared visual system, explicit metadata, no compressed inline loaders, no hidden template magic, and a clear separation between content, layout, and interaction.

The end goal is a website that is ready for the AI-assisted workflow without becoming dependent on AI to understand it. Boring is still the point.
